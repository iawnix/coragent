# Storage and recovery

The workspace manifest uses `research_workspace/3`, Nodes use `research-node/2`, and user Tasks use `coragent-user-task/6`. Deploy matching runtime, schemas and Skills together; there are no compatibility aliases or parallel readers for earlier Node/Task formats. Node `plan` holds hypotheses and the current investigation; notes preserve its history. Task retains objective, criteria, next action, execution plan and control without another scientific plan. Original requests, authored changes and execution observations have distinct sources. The unified Python namespace is `research_agent.research`; there is no parallel state or global-progress protocol.

Research Nodes have stable IDs and work directories under `research/nodes/<node_id>/`. Immutable Results preserve the Node revision and actual evidence they refer to. Records retain changes; indexes, reverse links, workspace/Node Markdown and bounded retrieval are rebuildable views. Change relationships without moving Node directories.

`Node.assessment_ref` selects one same-Node authored record or Result as the current research judgment. Save a new cited note and select it with `research_update {node_id, note, references, as_assessment:true}`; optional plan changes belong in that same request. The note records its exact references, selected identity and resulting Node revision in one transaction. Read conflicts save none of these changes. An ordinary note appends history without replacing the assessment or advancing the Node revision. Do not introduce a separate progress or memory file that must be synchronized with these records.

`operations/` holds runtime-owned dispatch, collection and delivery receipts. `artifacts/<id>/payload` and its manifest own fixed file bytes and provenance. Mutable Node work files must be registered before they become published materials. Pi owns session history; Memory survives a session and does not replace it.

Use public tools for managed research data, native file tools for work files. Transactions publish coherent updates; request receipts recover retries. An uncertain dispatch must be reconciled using its original identity, not repeated with a new Job. An uncertain email remains a delivery problem; rewriting Memory cannot resend it.

Old workspaces are unsupported and are not migrated or rewritten. Create a new workspace and explicitly import useful materials. Exact reference errors require inspecting the current object, not fabricating an ID or fallback location.

Object IDs are canonical workspace-scoped ordinals such as `node_1`, `result_1` and `art_1`; use returned IDs directly. Artifact reads take `artifact_id`, and prepared requests use `prepared_1`. IDs are never recycled; content hashes remain separate.

## Context and revisions

`research_context` is an observation saved at a particular time; the latest `runtime_control` snapshot carries task control and actual user submission IDs for its input binding. Earlier control snapshots remain historical observations. Neither is a new user instruction, even when carried in a user-role message. The Brief may omit objects or whole fields; use `research_read`/`research_search` for current records. Runtime task control can shorten continuation details; use `task_read` for the complete task. Read complete Node fields before replacing them; context and compressed summaries do not establish read receipts. On a stale-read conflict, reread and merge. Correct Results with `supersedes`, then review affected conclusions and reports. Closing a Node does not validate a scientific claim or complete the task.

The deterministic Brief prioritizes the selected assessment, including its limits and evidence references, over recent notes. It supplies the complete assessment or a read requirement; it does not silently trim a conclusion away from its qualifications or ask a second model to reconstruct missing content. A notice that evidence arrived after selection calls for review, not automatic rejection or replacement of the assessment. Task `next_action` remains the single concrete continuation instruction; entering a wait saves it together with the awaited Job IDs.

Search uses `kind`, for example `research_search({"kind":"result"})` for published Results or `{"kind":"result_published"}` for their publication records. There is no aggregate `kind="record"`; omit kind and use origin to filter user/runtime/agent records. `research_read({"ref":"<node_id>","field":"subjects"})` reads a Node's subjects. Read pagination counts Unicode characters, search pagination counts entries, and artifact_read pagination counts bytes.
